# Build and verify the native repository package

The repository root delivers the promoted engineering and productivity skills to Claude Code and Codex from their original directories. Both fork marketplace catalogs select `./`. Non-promoted directories remain in the repository; the native manifests expose only the promoted set.

## Inputs and ownership

Use this procedure when generating the Codex manifest after an authorized metadata or packaging change, checking package drift, changing marketplace routing, or preparing a consumer of the packaged skills. Ordinary skill use and unrelated documentation edits do not require generation.

The maintained sources are `skills/engineering/`, `skills/productivity/`, `.claude-plugin/plugin.json`, and `LICENSE`. Preserve upstream skill bytes, attribution, executable bits, and invocation settings. The upstream Claude manifest is the source of truth: it lists every promoted skill directory exactly once. Each selected directory must contain `SKILL.md` and `agents/openai.yaml`. Duplicate skill names, paths outside the promoted buckets, symlinks in selected trees, nested `SKILL.md` files, and version disagreement with `package.json` stop generation.

`scripts/build-plugin-package.mjs` generates only `.codex-plugin/plugin.json` from the upstream Claude manifest. Both native manifests select the same original directories. The Codex display name is "Skills for Real Engineers", with Matt Pocock named as its developer. The builder leaves the upstream manifest, license, skill trees, and other repository contents intact. The root uses native compatibility manifests; a root `plugin.json` would select a different Codex discovery mode and is rejected by the package check.

Use Node.js 22 or newer. The build and unit tests use Node's built-in modules and require no dependency installation. The compatibility regression also requires a Codex executable with the app-server `plugin/read` route. Read [the native Codex compatibility reference](codex-plugin-compatibility.md) when changing manifests, marketplace routing, or compatibility checks.

## Procedure

1. Record the candidate revision with `git rev-parse HEAD` and inspect `git status --short`. Confirm authorization for the intended source or packaging change and preserve unrelated work. A downstream consumer loads this procedure at its reviewed revision and verifies that the relevant source and package changes have a clean review before dependent execution. During producer self-use, record the candidate revision and rerun the checks below before review.
2. Run `npm run build-plugin-package` when the source manifest changes. Generation validates the promoted inventory and both catalog routes before updating only the native Codex manifest. If validation fails, resolve the source or routing decision within the task's authority before retrying. Skill content changes need no copies to refresh; both harnesses read the original directories.
3. Run `npm test`, `npm run check-plugin-version`, and `npm run check-plugin-package`. Check mode performs no writes. It rejects a missing or stale Codex manifest, an invalid promoted inventory, or catalog routing that does not select the repository root. Rebuild a stale derived manifest, then rerun verification. Compare authorized skill changes against the upstream revision separately; package checks establish selection and generated metadata consistency, not upstream provenance.
4. After manifest or marketplace changes, run `claude plugin validate . --strict` and `claude plugin validate .claude-plugin/marketplace.json --strict`. Validate the root package and the marketplace separately. The sole accepted warning is that root `CLAUDE.md` is not loaded as plugin project context: this file supplies repository guidance, while the manifests supply plugin skills. If strict root validation fails only for that warning, also run `claude plugin validate .` and require success with exactly that warning. Retain both results and the warning text. Every other warning or error remains a gate; marketplace strict validation must pass.
5. Before publication or dependent use, run `npm run test-codex-plugin` against the candidate and require success. It uses `codex` by default; set `CODEX_BIN` to the intended direct executable when selecting another installation. The test starts isolated app-server processes and exercises real discovery with the repository package and controlled fixtures. It checks exact promoted selection, non-promoted exclusion, native recursion, optional long description, and the portable format boundary. Retain the test output, including the reported Codex version. Consumers run this command with their own Codex executable on the reviewed package revision before dependent execution. Source evidence, unit tests, and an earlier executable's passing result do not replace this check. An unavailable executable or failed regression blocks that publication or use.
6. Before publication or dependent use, inspect the diff and verify both catalogs select `./`, both native manifests select the same promoted directories, and invocation metadata remains paired between `SKILL.md` and `agents/openai.yaml`. Complete the repository's independent review on the final revision, then follow `checkpointing-and-publishing-git-work` for publication. Consumers record that reviewed revision and run check mode on the same inputs before relying on the package.

The version workflow generates the Codex manifest after synchronizing the upstream Claude manifest version. CI rejects stale generated metadata and runs the Codex regression against `0.160.1` and the current `latest` package. Record the actual tested version from each run; this matrix does not establish a continuous supported version range.

## Completion evidence

Retain the reviewed revision, passing command results with the actual Codex version, the source-preservation comparison, and validation of each changed catalog or native manifest. Harness discovery requires separate evidence on the repository-root candidate: compare each harness's observed skill names with the promoted source manifest and confirm non-promoted names are absent. Preserve the source invocation metadata and report whether runtime enforcement was observed. Catalog parsing and session discovery establish neither marketplace installation nor workflow execution. Installation or host configuration changes need their own task authorization.

Capture useful corrections in this maintained procedure and rerun the affected checks and independent review. Publication, consumer acceptance, and changes to upstream skill behavior keep their existing owners.
